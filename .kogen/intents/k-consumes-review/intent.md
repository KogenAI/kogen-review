# Add consumes suites for each Kogen dependency

Slug: k-consumes-review
Model: not applicable — the change adds test suites and their READMEs; kogen-review's behaviour and state are unchanged

Kogen's repositories depend on each other through Go modules (kogen vendors kogen-loop). Each keeps a `contract/` suite for what it provides, but nothing states what a consumer relies on, so a producer's landing has to build and test every consumer in full (the blanket consumer check), which is slow and misses uses no test exercises. The owner's rule is two-sided contracts: each repository also states, as tests, exactly what it consumes. kogen-review keeps `contract/` (what it provides) unchanged and gains one suite per Kogen dependency, each stating exactly what kogen-review relies on from that producer:

- `consumes/kogen-coordinator/`: what kogen-review relies on from kogen-coordinator (module `github.com/KogenAI/kogen-coordinator`).
- `consumes/kogen-executor/`: from kogen-executor (module `github.com/KogenAI/kogen-executor`).
- `consumes/kogen-loop/`: from kogen-loop (module `kogen-loop`, which go.mod replaces with `github.com/KogenAI/kogen-loop`).
- `consumes/kogen-verification/`: from kogen-verification (module `github.com/KogenAI/kogen-verification`).

The suites pass at the versions go.mod pins now. Nothing else changes: `review/`, `cmd/`, `contract/`, `go.mod` and `go.sum` stay byte for byte as committed at HEAD, no command, flag or option is added (the only `main` package outside `features/` stays `github.com/KogenAI/kogen-review/cmd/kogen-review`), and kogen-review's behaviour is the same. `README.md` may gain one bullet naming `consumes/` in its Packages list; nothing else in it changes.

### What a use is

kogen-review's own code is the non-test Go files of the packages of module `github.com/KogenAI/kogen-review` outside `contract/`, `consumes/` and `features/` (today `review` and `cmd/kogen-review`). A use of a producer is every identifier in that code that resolves (go/types `Uses` or `Selections`) to an exported package-level object of a package of the producer's module, named `pkg.Name`, or to a method or field of one of its named types, named `pkg.Type.Member` by the type that declares the member (a promoted member by its declaring type). `pkg` is the last element of the package's import path. The acceptance observer, the Go program whose source `features/steps/k-consumes-review__observer.js` exports, computes exactly this and prints it with `-list`:

```sh
d=$(mktemp -d) && node -e "process.stdout.write(require('./features/steps/k-consumes-review__observer.js').source)" > "$d/main.go" && printf 'module observer\n\ngo 1.27\n' > "$d/go.mod" && (cd "$d" && go build -o observer .) && "$d/observer" -list . kogen-coordinator=github.com/KogenAI/kogen-coordinator kogen-executor=github.com/KogenAI/kogen-executor kogen-loop=kogen-loop kogen-verification=github.com/KogenAI/kogen-verification
```

### Each suite

- One Go package in `consumes/<producer>/` made only of `_test.go` files (any package name, for example `package consumes`), plus `README.md`. No non-test Go file, no subpackage needed, no build constraint, no `t.Skip`, no sleep.
- Written only against the producer's exported API. It imports only the standard library (never `net` or any `net/...` package), the producer's packages, and packages of the other three Kogen dependency modules only where a producer signature needs their values (for example `core.ProviderRole` takes a `project.Role` and returns a `provider.Role`, `core.ResponseTokens` takes a `*provider.Response`, `core.ShellDefinitions` takes a `*tools.Tools`). It never imports a package of kogen-review (`review`, `contract`) or any other module, and adds no go.mod requirement.
- Every use in its list is named by at least one of its tests, and asserted so that changing what kogen-review relies on fails the suite: the type or signature of each function, method, type, field and constant pinned at compile time with its types written out (as `contract/api_test.go` does), and, through real calls, the behaviour, values and formats kogen-review's call sites in `review/*.go` and `cmd/kogen-review/main.go` depend on (for example the exact stage strings of `route.StageReview`, `StageReviewVerify` and `StageReviewRetry`, the role, ending, reason and usage constants of `executor`, the bytes of `core.EncodeJSON` and `core.HashHex`, the JSON keys of `core.ReviewRecord`, `core.ExecutorState` and `core.ExecutorUsage` as kogen-review writes them, the class, reason, detail and exit of the stops made by `executor.Fail`, `executor.RoundLimit`, `core.ResumeRefused` and `sys.Fail`, the `git.Repo` methods on a Git repository made in `t.TempDir()`, `project.LoadConfig` of a `.kogen/project.yaml` written in `t.TempDir()`, the paths of `project.IntentDir`, `FeaturePath`, `ModelPath` and `ConfigPath`, and `verify.Pass.Results` text). A method of an interface (`executor.Executor`, `executor.Session`, `executor.PromptSizer`) counts as covered only when a test names it through the interface (a call on an interface value or a method expression), not by implementing it in a fake. A use that cannot run without the network, a model, a signed-in harness or a supervisor process (`provider.Client.Respond` sending, `executor.Executor.Start` of a real executor, `sys.MaybeSupervise` with the supervisor argument) is pinned by its signature and by the offline outcome kogen-review's call relies on where the producer documents one (for example `sys.MaybeSupervise` returning when its arguments do not start with the supervisor argument, as kogen-review's are). It asserts nothing kogen-review does not use: other exported identifiers of a producer may appear only to arrange or observe a use, and are not inventory items.
- Each assertion message names the inventory item it checks (as the contract suite's `eq(t, item, …)`).
- The same isolation as `contract/`: a `TestMain` that unsets every inherited `GIT_*` and `KOGEN_*` variable and `EMAIL`, sets a `HOME` of its own (`os.MkdirTemp`, removed afterwards), `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1` and `GIT_TERMINAL_PROMPT=0`. No network (no listener, no HTTP server, no fixed port), no host paths (every file under `t.TempDir()`; no read of kogen-review's sources, the module cache or another repository's files), no shared state between tests; deterministic under `-race -count=1 -shuffle=on` and `-trimpath`.
- `README.md`: what the suite pins (what kogen-review relies on from the producer, at the version go.mod pins), how to run it (`go test -race -count=1 ./consumes/<producer>/`), its isolation, how coverage was checked (the go/types listing above of every use in kogen-review's non-test code compared with the identifiers the suite's tests name), and a `## Inventory` section with one table row per use, whose first cell is the use in backquotes (for example ``| `git.Repo.Diff` | TestRepoDiff |``) and whose other cells name the tests asserting it. The inventory lists every use of the suite's list once and nothing else.

### Acceptance

The observer, run on the checkout, must print `ok`: each suite exists, has no non-test Go file and no forbidden import, its tests name every use, and its inventory equals its list. `go test -count=1 ./...` must pass with an `ok` line (not `[no tests to run]`) for each of the four consumes packages and `contract`; `go test -race -count=1 -shuffle=on ./consumes/...` must pass the same way with a Git dir, work tree and index that do not exist, a fresh `HOME` whose `.gitconfig` signs every commit and tag with a key that does not exist, `GOPROXY=off` and `GOFLAGS=-mod=readonly -buildvcs=false`. `features/steps/k-consumes-review__fixtures.js` holds known-good observer controls (bare references of every use, without tests), not the implementation: the Build writes real tests and does not copy them.

## Decisions
- One suite per Kogen dependency, `consumes/<producer>/` next to the kept `contract/`, written only against the producer's exported API with `contract/`'s isolation (source: request)
- The suites are written in the same style as `contract/` (compile-time pins with their types written out, assertion messages naming their inventory item, a README in the contract README's manner); no automatic step observes style, so it needs human evaluation by the reviewer, and no scenario claims it (source: request)
- Whether each test asserts the behaviour kogen-review relies on, beyond naming the use, needs human evaluation by the reviewer; the acceptance observer checks only that every use is named by a test and listed in the inventory (source: request)
- A suite asserts exactly what kogen-review's non-test code uses of its producer, and its README inventory lists those uses, checked by a go/types listing of the imported identifiers per dependency (source: request)
- The suites run in `go test ./...` at the pinned versions; no behaviour change, no new command, flag or option, go.mod and go.sum unchanged (source: request)

## Source comparison
- The request's suite path `consumes/kogen-coordinator kogen-executor kogen-loop kogen-verification/` names one folder per dependency, as its "one suite per Kogen dependency" and "Each consumes/<producer>/ suite" state: `consumes/kogen-coordinator/`, `consumes/kogen-executor/`, `consumes/kogen-loop/`, `consumes/kogen-verification/` (feature scenario 1 table; "Each suite").
- "in the same style": recorded in Decisions as needing human evaluation; "with the same isolation": the TestMain isolation and scenario 3's hostile environment.
- "no network, no host paths, no private helpers, deterministic": the import rule (no `net`, no kogen-review package), `t.TempDir()`-only files, the TestMain isolation and scenario 3's hostile environment with `-race -shuffle=on`.
- "nothing it does not use": the inventory must equal the use list exactly; helper use of other producer identifiers is allowed only to arrange or observe a use. Importing another Kogen dependency's package is allowed only where a producer signature requires it (observed: `core.ProviderRole`, `core.ResponseTokens`, `core.ShellDefinitions`), so a strict producer-only import rule is not imposed.
- "state how this was checked": each suite README's coverage paragraph and inventory; the acceptance observer is the executable check.
- The blanket consumer check of producers and the producers' repositories are out of scope; this Intent changes kogen-review only.

## Tests
- Each consumes suite covers every use of its producer in kogen-review's non-test code, with no forbidden import, no non-test file and an inventory equal to the uses: the four new `consumes/<producer>/` test packages, judged by acceptance scenario 1 through the go/types observer (integration)
- The suites run and pass in the normal `go test ./...` at the pinned versions: acceptance scenario 2 (integration)
- The suites are isolated from the caller's Git, HOME and module proxy and deterministic under the race detector and shuffled order: acceptance scenario 3 (integration)
- No behaviour change, no new command, go.mod and go.sum unchanged: the existing `review` and `contract` tests pass unchanged, and scenario 1's checks that `review/`, `cmd/`, `contract/`, `go.mod` and `go.sum` are as committed at HEAD and that the only main package outside `features/` is `cmd/kogen-review` (existing)
