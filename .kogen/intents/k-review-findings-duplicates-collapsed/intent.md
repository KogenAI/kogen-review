# Collapse duplicate review findings and cap them

Slug: k-review-findings-duplicates-collapsed
Model: not applicable — a stateless transformation of one submitted findings list (collapse, then a per-severity cut) inside verdict validation; no state or interacting rules
Acceptance:
- .kogen/intents/k-review-findings-duplicates-collapsed/acceptance.feature
- features/steps/k-review-findings-duplicates-collapsed__steps.js

The reviewer submits a verdict with `submit_review`. Verdict validation is `run.validate` in `review/independent.go`, the code behind the public `review.Validate(in, env, args, input)`. The native reviewer (`review.Independent`) and the external reviewer (`review.NewExternal`, through `verdictOf`) both run it, and kogen-build calls `review.Validate`. The `*review.Verdict` it returns is what is stored and handed on: `Session.Verdict` in the checkpoint, the `core.ReviewRecord` passed to `Env.Reviewed` and returned as `Result.Record`, the record file `review-<n>.json` (`review.File(n)`), the run log's `review` event, the `review: <path>:<line>: <message>` lines of the `candidate/review_blocked` stop, `Session.Blockers` and the `Account`'s blockers, and the retry feedback of an explicit resume. Today `validate` keeps every well-formed finding as submitted, so the same finding submitted three times reaches all of these three times, and the list has no size limit.

After this change, once each finding has passed today's shape and path checks (its path recorded clean, as today), `validate` turns the list of recorded findings into the verdict's findings in two steps:

1. **Collapse.** Two findings are the same finding when they have the same recorded (clean) path, the same line (the same integer value), the same severity, and the same message after `strings.TrimSpace`. Only the first-submitted copy of each finding is kept, with its fields as submitted (its message untrimmed) and its path clean. The kept findings stay in first-submitted order. Findings that differ in any of the four (for example only in line, or only in severity) are all kept.
2. **Cut.** The new constant `maxFindings = 50` in `review/independent.go`, with a doc comment, is the most findings of each severity a verdict keeps: at most 50 blocking and 50 note findings. Walking the collapsed list in order, a finding is kept while fewer than 50 findings of its severity have been kept, and otherwise dropped. The kept findings stay in their order. Duplicates removed in step 1 are not counted as dropped.

The verdict records the cut. `Verdict` gains the field `Dropped *Dropped \`json:"dropped,omitempty"\``, with the new exported type `Dropped struct { Blocking int \`json:"blocking"\`; Note int \`json:"note"\` }`: the number of blocking and of note findings step 2 dropped. It is nil when step 2 dropped nothing, so the verdict's JSON then has no `dropped` key. When anything was dropped, both counts are present (`{"blocking":10,"note":0}`). `review-<n>.json`, written by `evaluate`, gets the key `"dropped"` with the same object when the verdict's `Dropped` is non-nil, and no such key otherwise. `Session.Verdict` carries it through the checkpoint, as the JSON field of `Verdict`. A synthetic repair-stop verdict has one finding and no `Dropped`.

Every consumer listed above reads the verdict's findings, so all of them get the collapsed, cut list. No other consumer changes.

The other checks of `validate` keep their meaning. The changes/approve blocking rule ("a changes verdict needs at least one blocking finding", "an approve verdict cannot have blocking findings") is unchanged. A collapse always keeps one copy and the cut keeps up to 50 per severity, so a `changes` verdict whose blocking findings all collapse to one stays valid with that one finding. An `approve` verdict whose note findings are all copies of one keeps that one note. The requirements check (`run.requirements`, including the quote check of a changes verdict) gets the collapsed list before the cut. Problems are reported as today. A refused verdict has no findings and no `Dropped`.

Unchanged: the problem texts, the path rules, the requirements ledger, the reviewer prompt (`review/prompts/reviewer.md` and the golden files `review/testdata/prompts_golden.json` and `defs_golden.json`) and the `submit_review` definition. The reviewer is not told about the cut; it only shows in the record.

## Decisions
- Findings with the same path, line, severity and message, the message compared after trimming whitespace, are kept once, in first-submitted order, before the verdict is stored or handed on. (source: request)
- At most 50 blocking and 50 note findings are handed on, set by a documented constant. Findings past the bound are dropped in submitted order. (source: request)
- The stored verdict records how many blocking and how many note findings were dropped, so the cut is visible. (source: request)
- A verdict that still needs a blocking finding after collapsing keeps one. (source: request)
- The copy kept is the first submitted one, with its message as submitted (not trimmed). The path compared is the clean path the verdict records, so `dir/../a.txt` and `a.txt` are the same path. This follows the request's first-submitted order and the existing clean recording of paths. (source: request)
- One constant, `maxFindings = 50`, applies to each severity separately. This is the request's "a default of 50 blocking and 50 note findings". It is a package constant, not a setting, because the request asks for no setting. (source: request)
- The dropped counts are the field `dropped`, `{"blocking": <n>, "note": <n>}`, on the stored `Verdict` and in `review-<n>.json`. The field is absent when nothing was dropped, so verdicts under the bound are stored as before. (source: request)
- Duplicates are not counted as dropped. Only the cut is recorded, because the request asks the record to make the cut visible. (source: request)

- How the controls work: the step file's judgments compare the driver's observation with the feature's values. The bad control judges today's observed three kept copies of one blocking finding, and it must reject them.
