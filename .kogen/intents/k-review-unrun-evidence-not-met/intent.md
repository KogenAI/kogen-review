# Refuse unrun, failed or stale requirement evidence

Slug: k-review-unrun-evidence-not-met
Model: not applicable — each rule checks one submission against the pass under review, the candidate's current tree, the review's recorded shell runs and the requirements its earlier submissions listed; the review loop's stages, allowances, checkpoints and stop classes keep their transitions
Acceptance:

Today a review's requirement ledger (`submit_review`'s `requirements`, Intent k-review-intent-requirement-ledger) accepts any `acceptance` or `test` reference without looking at it, and a `probe` reference only needs to be the command of some shell call of the review. So an approval can mark a requirement met by naming an acceptance scenario that did not run, that failed, or that passed on an older tree, or by citing a successful `echo ok`. After this change, Kogen checks an approval's `acceptance` and `probe` entries against what it observed: the verification pass under review and the shell runs of this review, on the candidate's current tree. An entry whose evidence was not observed there is refused with its concrete status (not run, failed, another tree, did not succeed, exercises nothing of the candidate), for correction or a focused probe. An acceptance scenario that passed on the exact current tree establishes the requirement with no probe. A probe that ran in this review on the current tree, succeeded and names a file or directory of the candidate establishes it even when acceptance did not run. Earlier results are not altered or discarded: the pass and its record stay as they are, and the refusal names them as another tree's history. A requirement once listed cannot be dropped from a later approval of the same review. When nothing can verify a requirement, the reviewer keeps it unmet in a changes verdict whose blocking finding says the verification could not run; Kogen does not invent a product defect, and every existing ledger rule stays in force.

Kogen still does not read requirements out of the Intent or resolve `test` references (a green pass ran the configured checks; Kogen cannot map a test name to a requirement). A submission without `requirements` (absent or `null`) in a review whose earlier submissions listed none is validated exactly as today.

The reviewer's model-facing policy is not changed: `ReviewerInstructions()`, `review/prompts/reviewer.md`, `RequirementsRule`, `LimitRaises`, the `submit_review` definition, the external review task (`reviewTask`, `reviewPartsTask`, `reviewTaskTail`), `MaterialOf` and both goldens (`review/testdata/prompts_golden.json`, `defs_golden.json`) stay byte-for-byte as they are. The new texts reach a reviewer only as the problems of a refused submission. This keeps kogen-build's consumer tests that pin the reviewer's bytes (`TestContextExternalNativeBytes`, `TestKRevodGatePartsUnchanged`, `TestTheReviewerApprovesUnchangedCodeWithoutRepairs`), which an earlier candidate of this Intent broke by changing the prompt, passing unchanged.

The interface, all in package `review` (module `github.com/KogenAI/kogen-review`), in numbered items the sections below refer to:

1. Session (`review/independent.go`). `Session` gains two fields; with `omitempty`, sessions without them encode exactly as today:
   - `ProbeRuns []ProbeRun` with JSON tag `probe_runs,omitempty`. A new exported type `ProbeRun` has `Command string` (`command`), `Status *int` (`status`: the exit status the shell tool reported, `null` when its result has none) and `Tree string` (`tree`: the candidate's tree, `candidateTree`, right after the call). The native review appends one for every `shell` call wherever it appends to `Session.Probes` today (a non-empty string `command`, after the call returns; not the ignored calls after a verdict). `Status` is the integer N when the call's result text begins with `exit status: N` followed by a newline or the end of the text, and `nil` otherwise (for example a refused call).
   - `Listed []string` with JSON tag `listed_requirements,omitempty`: the `requirement` texts of every well-formed `requirements` array a submission of this review gave, accepted or refused, each once, in the order first listed. Both the native `submit_review` calls and the external reviewer's structured verdicts add to it.
   The `Session` literals that `retry` and `evaluate` rebuild carry `ProbeRuns` and `Listed` forward, as they carry `Probes`; checkpoints, resumes and working-window resets keep them.

## Decisions
- An acceptance entry establishes a requirement only when the scenario it names passed in a verification pass of the exact current tree; an unrun, failed or other-tree result is refused with its status, and the earlier result stays as history (source: request)
- A probe establishes a requirement only when it ran in this review on the current tree, succeeded and exercises the candidate; `echo ok` does not (source: request)
- When nothing can verify a requirement, the reviewer keeps it unmet in a changes verdict whose finding says verification could not run, not that the product is wrong; a listed requirement cannot be dropped from a later approval (source: request)
- The refusal is returned as the submission's problems for correction or a focused check, through the existing rejected-verdict path; the reviewer's instructions and tool definitions are unchanged (source: request)
