# Review a saved candidate from its on-disk state

Slug: k-review-saved-candidate
Model: not applicable — a test-only change: no product state, behaviour or format changes
Acceptance:
- .kogen/intents/k-review-saved-candidate/acceptance.feature
- features/steps/saved_candidate_steps.js
- features/steps/saved_candidate_observer.cjs

Prove that kogen-review's Review runs on its own: against a saved candidate (a candidate and its saved state as an earlier Build wrote them to disk) it gets a verdict without creating or starting a Build attempt. Review is moving to its own repository, and today every existing path to Review either goes through a Build attempt (kogen-build) or, in this repository, assembles the review's Input in memory: `TestReviewOfASavedCandidateWithoutABuild` (`contract/saved_candidate_test.go`, contract item `saved-candidate`) reviews a real Git candidate with a harness Env, but no saved state is ever read from disk and its resume uses the checkpoint the harness kept in memory. This change makes that test read the saved state from disk and review from it.

This is a test-only change (change_type: test). The `review` package (including `review/testdata/prompts_golden.json` and `review/testdata/defs_golden.json`), `go.mod` and `go.sum` stay byte-identical. No behaviour, format or CLI change, no new commands or flags, no timeout raised. Depends on K-REVIEW-SEAM (the narrow `review.Input`/`review.Env` contract over kogen-executor core), present at HEAD.

The test keeps its name `TestReviewOfASavedCandidateWithoutABuild` in `contract/saved_candidate_test.go`; update its harness (`savedCandidate`, `savedEnv`) in place:

1. Saved candidate. A real Git checkout in `t.TempDir()`: a start commit holding `.gitignore` with the bytes `.kogen/local/\n` (so the run folder stays out of the candidate tree that `savedEnv.Tree` computes with `git add -A`), the approved Intent at `.kogen/intents/fixture/intent.md` with the bytes `# Greet the world\n\nThe greeting says hello, world.\n`, and `greeting.txt` with `hello\n`; then the candidate commit changing `greeting.txt` to `hello, world\n`. T is that commit's tree (`git rev-parse HEAD^{tree}`).
2. Saved state, in the current persisted format. The test writes `<checkout>/.kogen/local/runs/a1b2c3d4/checkpoint.json` (run folder mode 0700, file 0600): a version 4 checkpoint as kogen-build writes it, a JSON object with the keys `version` (4), `identity`, `candidate` (T), `index` and `approval` (base64 strings), `state` and `recovery_raw` (null), where `state` is a `core.State` of the pinned kogen-executor encoded with `core.EncodeJSON`. The test declares its own envelope struct with those JSON keys (it must not import kogen-build). The state holds at least: `root` the checkout; `slug` `fixture`; `config` with `Models["review"]` = `reviewRole`; `intent_text` the Intent bytes; `start` the start commit; `start_tree`; `baseline` and `baseline_digests` (including `.kogen/project.yaml`); `excluded` `[]`; `run` {id `a1b2c3d4`, dir the run folder, log `<run folder>/log.jsonl`}; `git_index`; `phase` `building`; `round`, `pass` and `review` 1; zero `usage` and `attempt_usage` (`core.ZeroTokens()`); `last_pass` the green pass {n 1, clean, green, tree T}; `last_review` {n 1, verdict `approve`, findings `[]`, tree T}; `continuation` {stage `review_verify` (`route.StageReviewVerify`), `pass` and `base` that green pass, `review` the reviewer session encoded with `review.Session.Encode`: role `reviewRole`, one attempt {pass 1, tree T, verdict `approve`, no findings}, verdict `approve`, tree T}; and `approval_bytes` the base64 of the Intent bytes. The envelope candidate, the pass trees and the review trees all name T.
3. Load. The test reads `checkpoint.json` back from disk with `os.ReadFile`, decodes the envelope and its `state` into `core.State`, and asserts `version` 4 and that the envelope `candidate`, `last_pass.tree`, `continuation.pass.tree` and the tree of the session decoded with `review.DecodeSession` all equal T.
4. Input and Env from the loaded state only: `review.Candidate{Root: state.root, Start: state.start, Tree: envelope candidate}`, `review.Intent{Approval: base64-decoded approval_bytes, Role: config.Models["review"]}`, `review.Evidence{Pass: *last_pass}`, `Number: state.review`, `review.Run{ID: run.id, Dir: run.dir}`, native tools rooted at `state.root`. The `savedEnv` takes its root, start and Intent text from the state and writes run-folder files (`Env.Write`, hence the review record `review-<n>.json`) into `run.dir`.
5. Review. `review.Independent{}.Review` of that Input (no checkpoint) with the existing scripted answers (read_file `greeting.txt`, then submit_review `approve` with the one note finding) keeps every existing assertion: verdict `approve`; the one finding with message `says hello, world`; record tree and pass tree T; 0 repairs; 2 requests; the first request carrying `# Greet the world` and `+hello, world`; the second carrying the read_file result `1\thello, world`; `review-1.json` present in the run folder; the harness's last saved checkpoint at stage `review_verify`.
6. Resume. `review.Independent{}.Resume` with `in.Checkpoint` = `review.Checkpoint{Stage, Pass, Base, Session}` taken from the loaded `continuation` (not the harness's in-memory checkpoint) returns verdict `approve` with record tree and pass tree T and makes no model request (still 2 requests).

No Build attempt, Build state type or kogen-build import is involved. The test reads no file of another module's cache and none of kogen-build's state goldens (K-STATE-GOLDENS, `build/testdata/state/...` in kogen-build), which stay byte-identical and unregenerated there; this repository has no copy of them. Update the `saved-candidate` item of `contract/README.md` (and the `contract` line of the top `README.md`) to say the review's Input and its resume checkpoint come from a version 4 checkpoint read from the saved candidate's run folder.

Acceptance observes the test from outside through Go's test log: it compiles `./contract` with `go test -c`, runs the binary in `contract/` with `-test.count=1 -test.timeout=10m -test.testlogfile=<file>` (the test log records every file the tests open as a line `open <path>`; 10m is go test's own default timeout), and requires PASS, an `open` of some `<checkout>/.kogen/local/runs/<id>/checkpoint.json` followed later by an `open` of a `review-<n>.json` in that same run folder, and no `open` of a path under `go env GOMODCACHE` or containing `/testdata/state/`. A second scenario requires every file under `review/`, `go.mod` and `go.sum` to be as committed at HEAD.

## Decisions
- No UI/UX surface. The test creates its own saved candidate (a real Git repository with a candidate commit, the approved Intent and saved state in the current persisted format whose candidate, pass and review trees all name that commit's tree) instead of using kogen-build's K-STATE-GOLDENS checkpoint fixture, whose envelope candidate tree (5555…) differs from its pass and review trees on purpose (source: request)

- addressed: "Do not read fixtures from another module's cache": no `open` under `go env GOMODCACHE`
- addressed: "No behaviour, format or CLI change; no new commands or flags; no timeout raised": scenario "The change is test-only"; acceptance uses go test's default timeout
- superseded: an earlier attempt's acceptance requiring kogen-build's `build/testdata/state/review-approve/checkpoint.json` as the saved candidate; replaced, as the request directs, by the test's own saved candidate whose trees all name its commit's tree
- preserved: the existing `saved-candidate` assertions (verdict, finding, trees, requests, read_file delivery, review record, resume without a request)

## Tests
- A review of a saved candidate gets a verdict from the saved state read from disk, with no Build attempt: update `TestReviewOfASavedCandidateWithoutABuild` in `contract/saved_candidate_test.go` to write the version 4 checkpoint, read it back and build the review's Input from it (integration)
- A resume from the saved state's continuation judges the saved approval without a model request: the same test resumes from the loaded `continuation` (integration)
- No behaviour, format or golden change: the existing suite passes unchanged and acceptance scenario "The change is test-only" (existing)
