# Give each prose-only streak its own reminder

Today the native reviewer (`review.Independent`, `run.converse` in `review/independent.go`) spends its one prose-only allowance once per review. A prose-only turn is a model response with no tool call. The first one gets a reminder, and the next request requires `submit_review` (forced where the route supports it). Any later prose-only turn ends the review with `no_tool_reminder_exhausted`, even when the reviewer answered the forced request with a `submit_review` that was sent back and then kept working. A green candidate then ends as a repeated invalid review.

After this change, the allowance is spent once per run of consecutive prose-only turns. Any tool call by the reviewer since the last reminder restores it, including a `submit_review` that was sent back. The next prose-only turn then gets the same reminder and the same required request. A fixed cap of 3 reminders per review bounds this, and the saved review counts them, so a resume does not reset the count. A review that still ends because of prose-only turns records its exact cause: the number of prose-only turns, the number of forced requests, how many of those were answered with a tool call, and the route and model. That record tells a reviewer that never calls the tool on a route apart from one that was cut off after working.

Unchanged: the rejected-verdict allowance, the unread-progress exemption, the working budget (twelve requests, then every request requires `submit_review`), the reminder text, how a required request is forced or sent as text, the `review_tool_choice` and `provider_fault` events, and the reviewer's model-facing policy (`ReviewerInstructions()`, `review/prompts/reviewer.md`, the `submit_review` definition and both goldens in `review/testdata/`). The external reviewer (`review.External`, `review/external.go`), `InvalidError`, `InvalidRecord` and the stdout keys of `cmd/kogen-review` are also unchanged. The only visible effect there is that `invalid.reason` can now be `no_tool_reminder_cap`. For a review that submits, or that has at most one prose-only turn, every `Env.Request` (its count, order, `Instructions`, `Input`, `Tools` and `ForceTool`) is exactly as today.

The interface, all in package `review` (module `github.com/KogenAI/kogen-review`), in numbered items the sections below refer to:

1. Session (`review/independent.go`). `Session` gains four fields, directly after `NoTool` and in this order, all `omitempty`, so a session without them encodes exactly as today:
   - `Restored bool`, JSON `no_tool_restored`: the reviewer made a tool call since the last reminder of this review.
   - `ProseTurns int`, JSON `prose_turns`: the prose-only turns of this review.
   - `ForcedRequests int`, JSON `forced_requests`: the answered requests of this review that required `submit_review`. These are the requests for which `converse` records the `review_tool_choice` event: a reminder request (`Remind`) or a request over the working budget, in either mode (`api_forced` or `text_fallback`). Each one is counted once, when its response arrives, so an interrupted request that is sent again after a resume is not counted twice.
   - `ForcedAnswered int`, JSON `forced_answered_with_tool`: those of `ForcedRequests` whose response had at least one tool call (any tool).
   `NoTool` (JSON `no_tool_reminders`) keeps counting the reminders this review gave, now up to the cap. The comments on `Session` and `converse` that describe "one prose-only turn" are updated to the rule below.

2. The rule (`run.converse`). An unexported constant `noToolReminderCap = 3`. After each response, before the existing `switch` that spends the allowances, `converse` updates the session:
   - if the request required `submit_review` (item 1), `ForcedRequests++`, and also `ForcedAnswered++` when the response had a tool call;
   - if the response had a tool call and `NoTool >= 1`, `Restored = true`;
   - if the response had no tool call, `ProseTurns++`.
   A prose-only turn that the unread-progress exemption does not cover (today's `problems != nil && len(calls) == 0` case) then has exactly one of three outcomes:
   - `NoTool == 0`, or `Restored` and `NoTool < noToolReminderCap`: the reminder, as today. The same user message `Not a valid verdict: the review ended without calling submit_review. Call submit_review.` is appended, `NoTool++`, `Remind = true` and `allowance("no_tool_turn")` is recorded. In addition, `Restored = false`.
   - `NoTool >= 1` and not `Restored`: `invalidStop(problems, "no_tool_reminder_exhausted", force != "")`, as today.
   - `Restored` and `NoTool >= noToolReminderCap`: `invalidStop(problems, "no_tool_reminder_cap", force != "")`. No request follows.
   The problems stay `["the review ended without calling submit_review"]`. A prose-only answer to a forced request records the `provider_fault` event (`forced_tool_not_called`) exactly as today. Because `Restored` is false right after a reminder, a prose-only answer to a reminder's request ends the review with `no_tool_reminder_exhausted`.

3. The record and hand-off (`review/invalid.go`, `review/contract.go`). `Invalid` gains these fields directly after `NoToolReminder`: `ProseTurns int`, `ForcedRequests int`, `ForcedAnswered int`, `Route string`, `Model string`, `ToolChoice string`. For the reasons `no_tool_reminder_exhausted` and `no_tool_reminder_cap`, `invalidStop` sets them as follows:
   - `ProseTurns`, `ForcedRequests` and `ForcedAnswered` are the session's counters.
   - `Route` is `provider.Name(core.ProviderRole(r.sess.Role))` and `Model` is `r.sess.Role.Model`.
   - `ToolChoice` is `api_forced` when `provider.SupportsToolChoice(core.ProviderRole(r.sess.Role))`, else `text_fallback`.
   For those two reasons, the run log's `review` event with verdict `invalid` gains the keys `prose_turns`, `forced_requests`, `forced_answered_with_tool`, `route`, `model` and `tool_choice`, with the same values. Its existing keys (`event`, `review`, `verdict`, `problems`, `reason`, `rejected_verdicts`, `no_tool_reminders`) stay. `NoToolReminder`, `RejectedVerdict`, and `ForcedRoute`/`ForcedModel` (set only when the stopping request was forced) keep their meaning. For any other reason, the new fields stay zero and the event gets no new keys.

4. Carried state. The `Session` literals that `evaluate` (a repair round) and `retry` (the reopened blocked review) rebuild carry `NoTool`, `Restored`, `ProseTurns`, `ForcedRequests` and `ForcedAnswered` forward, so the cap and the counts belong to the whole review. `Rejected`, `Remind` and `PrevUnread` start afresh there, as today. Checkpoints, resumes and working-window resets keep all five fields, as they keep the other session fields.

5. Pins and docs. Update `contract/README.md`: its `independent-invalid` item, plus new items named next to their tests. Pin the new `Session` keys in `contract/formats_test.go` and the new `Invalid` fields in `contract/api_test.go`. No golden is rewritten.

## Decisions
- The prose-only allowance is spent once per run of consecutive prose-only turns: any tool call by the reviewer since the last reminder restores it, including a `submit_review` that was sent back (source: request)
- The reminder for a restored allowance is the same reminder and the same required request as the first one, forced where the route supports it and text otherwise (source: request)
- At most 3 reminders per review (the value is Kogen's choice, as the request leaves it), counted in the saved review (`no_tool_reminders`), so a resume continues the count. The count also carries through repair rounds and the reopened review, so the cap is per review (source: request)
- A review that ends because of prose-only turns names its exact cause: `no_tool_reminder_exhausted` (no tool call since the last reminder) or `no_tool_reminder_cap` (the cap reached after working). Its record carries the prose-only turns, the forced requests, how many of those were answered with a tool call, and the route, model and tool-choice mode (source: request)
- The rejected-verdict allowance and the unread-progress exemption are unchanged. A review that submits, or that has at most one prose-only turn, sends the same requests as today (source: request)
