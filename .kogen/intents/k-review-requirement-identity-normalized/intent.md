# Identify review requirements by normalized text

Slug: k-review-requirement-identity-normalized
Model: not applicable — each rule checks one submit_review call against the requirement texts earlier submissions of the same review listed; the review loop's stages, allowances, checkpoints and stop classes keep their transitions
Acceptance:

Today a review's requirements (`submit_review`'s `requirements`) are identified by their exact text (`run.requirements` in `review/independent.go`). Once a submission lists a requirement (`Session.Listed`), a later approval must list the same exact string. If a resubmission changes only case or whitespace, the old text is reported as missing (`requirement "<R>" was listed by an earlier submission of this review and is missing: ...`) and the new text becomes a second entry of `Session.Listed`. One submission that lists the same text twice keeps both entries, even when their `met` values differ. A changes verdict's blocking finding must contain the requirement's exact text.

After this change, a requirement's identity is its text with leading and trailing whitespace removed, each run of whitespace replaced by one space, and letter case ignored. In Go: `strings.ToLower(strings.Join(strings.Fields(text), " "))`. Every requirement comparison uses this identity: retention across submissions, duplicates within one submission, and the quote check of a changes verdict. The text first listed in the review is the one stored and shown. Requirements that differ in words stay different. Nothing else changes: the shape check and its problem, the evidence checks and problems, `ref` matching against probe commands (still exact), the reviewer's instructions and `submit_review` definition (and so both goldens), the record keys, the stop classes, the allowances, `cmd/kogen-review` and the external reviewer's flow (it goes through the same validation).

The rule, in `run.requirements` (reached by the native reviewer, the external `verdictOf` and `review.Validate`):

1. Absent or `null` `requirements` and a malformed array behave as today. A malformed array gives only the existing shape problem and does not change `Session.Listed`.
2. A well-formed array's entries are grouped by identity, in order of each identity's first entry. A group's stored text is the text of `Session.Listed` with that identity when the review already listed it. Otherwise it is the text of the group's first entry, and that text is appended to `Session.Listed`. So `Session.Listed` holds each identity once, with its first spelling, whether the submission is accepted or refused. Several `Listed` texts can share an identity only in a checkpoint written before this change. There, the first such text in `Listed` order is the stored text, and an entry with that identity satisfies all of them.
3. Some entries of a group can differ from its first entry in `evidence`, `ref` (exact string comparison, because a probe `ref` must stay the exact shell command) or `met`. Such a group gives exactly one problem, in place of any per-entry problem of its entries: `requirement "<R>" is listed twice: list each requirement once in requirements, with one evidence, ref and met`. This applies to every verdict, `approve` and `changes`. `<R>` is the group's stored text.
4. A group whose entries all agree is one entry: the stored text with the first entry's `evidence`, `ref` and `met`. It goes through the existing checks in their existing precedence, and every problem quotes the stored text as `<R>`. The changes-verdict quote check passes when a finding with severity `blocking` has a `message` whose identity contains the requirement's identity as a substring. The problem text is unchanged.
5. Problems come in group order, then the missing problems. For an approval, each text of `Session.Listed` as it stood before this submission gets the existing missing problem, in `Listed` order, when no group has its identity. The problem quotes the listed text.
6. An accepted verdict's `Verdict.Requirements`, and so the `"requirements"` of `review-<n>.json`, are the groups' entries in group order, each with its stored text.

Examples: the review listed `The tool prints a total`, and a later approval lists `  the TOOL prints   a total ` with valid evidence. The approval is accepted, nothing is reported missing, and the record keeps `The tool prints a total`. In one submission, `prints a total` and `prints a total in bytes` are two requirements.

Implementation also updates the doc comments of `Session.Listed` and `run.requirements`, and the `validate-requirements` and `session-listed` items of `contract/README.md`, to state the identity.

## Decisions
- A requirement's identity ignores leading and trailing whitespace, treats each run of whitespace as one space, and ignores letter case. Requirements that differ in words remain different (source: request)
- A submission that lists the same identity twice is refused with a problem that names the requirement and says it is listed twice. When both entries agree on evidence, ref and met, they are kept once instead (source: request)
- The text first listed is the one stored and shown: in the record, in `Session.Listed` and in every problem about that requirement (source: request)
- A changes verdict's blocking finding quoting the requirement matches under the same identity (source: request)

## Source comparison
- Problem: "A resubmission that only changes case, trailing punctuation, or the amount of whitespace ... is treated as a different requirement". The request's Need defines identity only through whitespace and letter case, and says "Requirements that differ in words remain different". The Need is the stated contract, so trailing punctuation stays significant: `prints a total.` and `prints a total` are still two identities. Case and whitespace are addressed by rules 2–6.
- Need "identity ignores leading and trailing whitespace, collapses runs of whitespace to one space, and ignores letter case": the identity function above. Scenarios 1, 2, 4 and 7.
- Need "A submission that lists the same identity twice is refused with a problem naming the requirement and saying it is listed twice, unless both entries agree on evidence, ref and met, in which case they are kept once": rules 3 and 4. Scenarios "One submission listing a requirement twice with different met values is refused" and "... with the same evidence, ref and met is kept once". Two technical details were decided in shaping. A conflicting identity gets only the "listed twice" problem, not also the per-entry problems of its entries. "Agree" compares `ref` as an exact string.
- Need "The text first listed is the one stored and shown": rules 2, 4 and 6. Scenarios 1, 4 and 5 check the record, and the problems of scenarios 2 and 7 quote the first spelling.
- Need "Requirements that differ in words remain different": scenarios "Requirements that differ in words stay two requirements in one approval" and "A listed requirement that differs in words is still missing when only the shorter one is kept". Both rule out a substring identity.
- Synthetic acceptance 1: scenario "A later approval may respell a listed requirement, and the first spelling is stored", with the literals `The tool prints a total` and `  the TOOL prints   a total `. Today that approval is refused as missing the first text, and the review ends invalid.
- Synthetic acceptance 2: scenario "An approval that omits a listed requirement still reports it missing, once". Its first submission also lists a case variant, which today gives two problems and two `Listed` entries.
- Synthetic acceptance 3: scenario "One submission listing a requirement twice with different met values is refused". It uses a changes verdict, which today keeps both entries.
- Synthetic acceptance 4: scenario "One submission listing a requirement twice with the same evidence, ref and met is kept once".
- Synthetic acceptance 5: scenarios 5 and 6, with the literals `prints a total` and `prints a total in bytes`.
- Synthetic acceptance 6: scenario "A changes verdict's blocking finding quotes an unmet requirement under the same identity". A finding that differs in words is still refused.
- The scenarios run the native reviewer (`review.Independent`, the entry kogen-build uses) through a Go driver with a scripted model and a green pass. Evidence `test` is valid evidence that Kogen does not resolve today, so the scenarios need no probe or acceptance run.
- Omitted (not requested): normalizing punctuation or Unicode forms, changing `ref` or probe matching, changing the reviewer's instructions or the `submit_review` definition.

## Tests
- Agreeing entries whose texts differ only in case or whitespace are kept once, with the first spelling: new test `TestValidateIdentifiesRequirementsByNormalizedText` in `contract/validate_test.go`, through `review.Validate`. It covers an approve with `R1` and ` r1 ` (same evidence, ref and met) accepted with one entry `R1`. (unit)
- An identity whose entries differ in `met`, `evidence` or `ref` is refused with exactly the "listed twice" problem naming the first spelling, for both an approve and a changes verdict: same new test, one case per differing field. (unit)
- Requirements that differ in words stay separate: same new test, `prints a total` and `prints a total in bytes` give two entries. (unit)
- A changes verdict's unmet requirement is quoted by a blocking finding whose message matches it only after case and whitespace normalization, and is still refused when the message differs in words: same new test. (unit)
- Across submissions of one native review, a respelled approval is accepted with the first spelling stored, `Session.Listed` holds one text for the identity, and an approval that omits it is refused with the missing problem: extend `TestIndependentReviewJudgesACitedProbeByItsLatestRun` (item `session-listed`) in `contract/independent_test.go`, asserting the decoded checkpoint's `Listed`.
