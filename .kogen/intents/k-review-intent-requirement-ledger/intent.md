# Require evidence per requirement before approval

Slug: k-review-intent-requirement-ledger
Model: not applicable — each rule is a check of one submit_review call against the review's recorded shell commands; the review loop, its stages, allowances and checkpoints keep their current transitions
Acceptance:
- .kogen/intents/k-review-intent-requirement-ledger/acceptance.feature
- features/steps/requirement_ledger_steps.js
- features/steps/requirement_ledger_controls/observe.sh
- features/steps/requirement_ledger_controls/good.patch

Today the reviewer reads the diff, runs one round of generic probes and approves. Nothing asks it to check each requirement of the approved Intent against evidence. Its instructions also tell it that correct code usually needs three rounds. As a result, a green candidate that misses a stated requirement which no test or acceptance step exercises gets a clean approval. After this change, before any verdict, the reviewer works through the Intent's concrete, observable requirements one by one. For each one it names the evidence that the candidate meets it: an existing test or acceptance step that exercises it, or a probe it ran with `shell` against the candidate in this review. It probes every requirement that has no evidence. It repairs a requirement that the probe shows missing or wrong, or blocks on it with the requirement quoted. It records this mapping in a new `requirements` field of `submit_review`. Kogen enforces the parts it can check deterministically. It rejects an approval with an entry that has no evidence, is not met, or (native reviewer only) cites a probe that did not run in this review. It rejects a changes verdict that leaves an unmet requirement unquoted. It keeps the mapping in the review record. A candidate whose requirements all have evidence costs no extra request or round.

Kogen does not read requirements out of the Intent itself. Judging which sentences are concrete and observable belongs to the reviewer. Its instructions require that judgment, and Kogen checks only the entries the reviewer submits. A submission without `requirements` (absent or `null`) is validated exactly as today. This keeps the external executor's structured verdicts, kogen-build's callers and fakes, the saved-candidate formats and earlier acceptance working unchanged. What changes: the reviewer's instructions (a new rule, and the batching paragraph's "three rounds" sentence), the `submit_review` definition, verdict validation, the reviewer session (it now records its shell commands), the review record `review-<n>.json` and the external review task text. Unchanged: `cmd/kogen-review` and its stdout keys, the stop classes and exit codes, the allowances, `core.ReviewRecord`, the run-log `review` event, and every existing contract test and format pin.

The interface, all in package `review` (module `github.com/KogenAI/kogen-review`), in numbered items that the sections below refer to:

1. Policy (`review/policy.go`). Add the exported constant `RequirementsRule`, a single line with exactly this text:

   `Requirements: before any verdict, work through the approved Intent's concrete, observable requirements one by one and name, for each, the evidence that the candidate meets it: an existing test or acceptance step that exercises it, or a probe you ran with shell against the candidate in this review. A test or step is evidence only for the inputs it exercises: when a requirement states or implies an empty, zero or limit input that none exercises, that input needs a probe. Probe each requirement without evidence before the verdict, in your probe round, with a small focused run of the inputs it states or implies, including that empty, zero or limit input. A probe that shows the behavior missing or wrong is a substantive defect: repair it with regression coverage or, when that is not possible within the approved scope, submit changes with a blocking finding whose message quotes the requirement. Sentences that are not observable, such as a statement of purpose, and wording that only restates the acceptance scenarios need no probe of their own. Record the mapping in submit_review's requirements, one entry per requirement: requirement (quoted from the Intent), evidence (test, acceptance, probe, or none while nothing exercises it), ref (the test or acceptance step, or the exact shell command of the probe; empty for none) and met (whether that evidence shows the candidate meets the requirement). Kogen rejects an approval with an entry whose evidence is none or whose met is false and, when it sees your tool calls, one whose probe command did not run in this review; a changes verdict quotes each unmet requirement in a blocking finding.`

   `ReviewerInstructions()` becomes `promptFile("reviewer") + "\n" + LimitRaises + "\n" + RequirementsRule + "\n"`. `Prompt(onDemand)` keeps building on it.

2. Batching paragraph (`review/prompts/reviewer.md`). Replace exactly `run your focused probes (stated limits, empty or zero values, error paths) in one combined shell command where possible. Code that proves correct usually needs only three rounds:` with `run your focused probes (each requirement without evidence, stated limits, empty or zero values, error paths) in one combined shell command where possible. Code whose requirements all have evidence usually needs only three rounds:`. The rest of the file stays byte-for-byte unchanged.

3. `submit_review` definition (`submitReviewDef`). The description becomes `Submit the review: verdict approve or changes, with findings and the evidence for each requirement.`. `parameters.properties` gains `requirements`, given here as plain JSON built from `map[string]any`/`[]any`, after `findings`:
   `{"type": "array", "items": {"type": "object", "properties": {"requirement": {"type": "string"}, "evidence": {"type": "string", "enum": ["test", "acceptance", "probe", "none"]}, "ref": {"type": "string"}, "met": {"type": "boolean"}}, "required": ["requirement", "evidence", "ref", "met"]}}`.
   `parameters.required` stays `["verdict", "findings"]`. The external reviewer's schema (`reviewSchema()`) follows it automatically.

4. Types (`review/independent.go`). `Verdict` gains the field `Requirements []Requirement` with JSON tag `requirements,omitempty`. A new type `Requirement` has the fields `Requirement`, `Evidence`, `Ref` (strings) and `Met` (bool), with JSON tags `requirement`, `evidence`, `ref` and `met`. `Session` gains `Probes []string` with JSON tag `probes,omitempty`: the `command` argument of every `shell` call this review session ran, in order. It is appended after the tool call returns, whenever the argument is a non-empty string, including calls that are not meant as probes. The ignored calls that follow a verdict in the same response are not recorded. The `Session` literals that `retry` and `evaluate` rebuild carry `Probes` forward, and checkpoints and resumes keep it. A fresh `Review` starts with none. Because of `omitempty`, sessions and verdicts without these fields encode exactly as today.

5. Validation (`run.validate`, also reached through `review.Validate` and the external `verdictOf`). When `requirements` is absent or `null`, nothing new is checked and `Verdict.Requirements` is nil. Otherwise it must be a JSON array whose every element is an object with `requirement` (a non-empty string), `evidence` (one of `test`, `acceptance`, `probe`, `none`), `ref` (a string, non-empty unless `evidence` is `none`) and `met` (a JSON boolean). If anything is malformed, the validation adds exactly one problem, `requirements must be a JSON array of objects with requirement (a non-empty string), evidence (test, acceptance, probe or none), ref (a string, non-empty unless evidence is none) and met (a boolean)`, which discloses no submitted content, and adds no per-entry problems. If the array is well-formed, each entry adds at most one problem, in entry order and in this precedence. `<R>` is the entry's `requirement` verbatim between straight double quotes:
   - verdict `approve` and evidence `none`: `requirement "<R>" has no evidence: probe it with shell against the candidate before the verdict`
   - verdict `approve` and `met` false: `requirement "<R>" is not met: repair it, or submit changes with a blocking finding that quotes it`
   - verdict `approve`, evidence `probe`, the native reviewer (not `External`), and `ref` is not exactly the `command` of a shell call of this review: `requirement "<R>" cites a probe that did not run in this review: run its command with shell before citing it`. A shell call counts when its command is in `Session.Probes` or when it is a `function_call` item named `shell` in the conversation `input` given to validation (so `review.Validate(in, env, args, input)` accepts a probe present in `input`). The external reviewer's tool calls are invisible to Kogen, so this check does not apply to it.
   - verdict `changes` and `met` false, when no finding with severity `blocking` has a `message` containing `<R>` (no quotes) as a substring: `requirement "<R>" is not met: a changes verdict needs a blocking finding whose message quotes it`
   - Every other entry is accepted. This includes evidence `none` in a changes verdict, and `test`/`acceptance` refs, which Kogen does not resolve.
   Requirement problems come after the existing finding and verdict-count problems and before the unread-parts problem. They are ordinary verdict problems. The native reviewer sends them back as the `submit_review` tool result `invalid verdict:\n<problems joined by \n>`, and the external reviewer gets them through its existing feedback text. They spend the one rejected-verdict allowance exactly as any other rejection does, with no new exemption. An accepted verdict carries the well-formed entries in `Verdict.Requirements`.

6. Record. `evaluate` writes `review-<n>.json` with a new key `"requirements"`: the verdict's entries as submitted (`{requirement, evidence, ref, met}` objects in order), or `[]` when there are none. The existing keys stay as they are.

7. External task (`review/parts.go`, `reviewTaskTail`). After the `LimitRaises` line, insert `RequirementsRule + "\n"`. The final sentence's first part becomes `Finish with the structured verdict: verdict approve or changes, findings {path, line, severity blocking|note, message} and requirements {requirement, evidence test|acceptance|probe|none, ref, met}.`. The sentences that follow it are unchanged.

8. Pins. Rewrite `review/testdata/prompts_golden.json` and `defs_golden.json` with `go test ./review -update` after these edits. In `review/policy_test.go`, update `reviewerBatchParagraph` to the new paragraph and the pinned hash to the new bytes. Add the new contract items to `contract/README.md` next to their tests.

## Decisions
- The reviewer works through the Intent's concrete, observable requirements one by one before its verdict. For each, it names an existing test or acceptance step that exercises it, or a probe it ran against the candidate in this review (source: request)
- A requirement with neither is probed before the verdict. A probe that shows the behavior missing or wrong is a substantive defect: the reviewer repairs it or, if it cannot within scope, reports it as blocking with the requirement quoted (source: request)
- Sentences that are not observable, and wording that only restates the acceptance, need no separate probe and produce no finding (source: request)
- Probes are added only for requirements without evidence, so a candidate whose requirements all have evidence costs no extra round (source: request)
- A probe of a requirement that the tests exercise only with ordinary input uses the empty or zero input (source: request)
- The mapping is recorded in `submit_review`'s `requirements` and kept in `review-<n>.json`, and Kogen enforces the checkable parts listed above; the request leaves how the mapping is recorded to Kogen (source: request)

## Source comparison
- "the reviewer should work through the Intent's concrete, observable requirements one by one and, for each, name what shows the candidate meets it: an existing test or acceptance step ..., or a probe the reviewer ran against the candidate in this review": addressed by `RequirementsRule` in the native instructions and the external task, the `requirements` entries (`evidence` test, acceptance, probe or none; `ref`; `met`), the native probe-ran check (item 5) and scenario "An approval that cites a probe the review did not run is sent back until the probe runs".
- "A requirement with neither is probed (a small focused run) before the verdict; if the probe shows the behaviour is missing or wrong, that is a substantive defect the reviewer repairs or ... reports as blocking with the requirement quoted": addressed by the rule, the rejection of an approval with evidence `none` or `met` false, and the changes-verdict quote check. Synthetic acceptance 1 is scenario "A requirement the candidate omits is probed and blocks instead of being approved". `cmd/kogen-review` verifies no repairs, so the scenarios exercise the blocking branch, and the repair branch stays the existing repair-and-verify loop.
- "Requirements that are not observable, and wording that only restates the acceptance, need no separate probe": addressed by the rule's sentence and by evidence `acceptance`. Synthetic acceptance 4 is scenario "A statement of purpose and a requirement the acceptance states need no probe and no finding".
- "This adds probes only for requirements without evidence, so a candidate whose requirements are all exercised costs no extra round": addressed by the reworded batching paragraph and by the absence of any new request or Kogen-side round. Synthetic acceptance 3 is scenario "Requirements that tests all exercise are approved without a probe in today's two requests".
- Synthetic acceptance 2 (C works, untested: probe once, approve, no finding): scenario "A requirement no test exercises is probed once and, when it holds, approved".
- Synthetic acceptance 5 (violated only on empty or zero input; the probe uses that input): scenario "A requirement broken only on empty input is probed with the empty input and blocks", plus the rule sentence about inputs a test does not exercise. Which input a model probes is the model's behavior. Kogen's part is the instruction and the blocking path, and the scripted model in the scenario shows that path end to end.
- "a review whose scripted model would otherwise approve": the scenarios script a loopback OpenAI-compatible model through the existing `cmd/kogen-review` steps. In scenario 1 the scripted approval that lists C without evidence is what Kogen now sends back. Today it is accepted at the first request with exit 0.
- "How the reviewer records the mapping is Kogen's choice": decided as the optional `requirements` field (items 3–6).
- Omitted (not requested): extracting requirements from the Intent in Kogen, resolving `test`/`acceptance` refs, new stdout keys of `cmd/kogen-review`, and changes to the allowances or stop classes.
