# Make rejected review verdicts informative

Slug: review-rejected-verdicts-informative
Model: not applicable — the change is a rule text and a progress line, with no state that interacting rules could corrupt
Acceptance:
- .kogen/intents/review-rejected-verdicts-informative/acceptance.feature
- features/steps/review-rejected-verdicts-informative__steps.js

Rejected review verdicts waste review rounds and their output does not say what went wrong. This Intent makes the reviewer's ref rule say what an acceptance ref contains, and makes every refusal progress line say how many problems there are, including the refusal that ends the review. It replaces the earlier narrow requests review-rule-acceptance-ref-names-scenario and review-rejected-verdict-line-counts-problems.

In review/policy.go, `RequirementsRule` has the text `ref (the test or acceptance step, or the exact shell command of the probe; empty for none)` replaced exactly by `ref (for test, the test; for acceptance, the scenario's name exactly as written after Scenario: in acceptance.feature, or the text of a step that occurs in that one scenario only, never a driver test or test method name; for probe, the exact shell command; empty for none)`. Every other character of the constant stays. The native reviewer instructions, the external one-session review task and the external part task keep carrying the rule through the constant, exactly once each.

The rejected-verdict progress line is built by one helper in review/invalid.go. With exactly one problem it is exactly `kogen: review N: verdict not accepted: <first problem>` as today. With more than one it is `kogen: review N: verdict not accepted (first of K problems): <first problem>`, where K is `len(problems)`, the full list before the 10-entry cap of the review_allowance event. The first problem is cut by `cutAtWord` at `progressProblemRunes` (160 runes); the ` (first of K problems)` prefix is not counted in that limit. The helper is called from `allowance` (a rejected verdict that is retried) and, before `invalidStop`, from the two `rejected_verdict_exhausted` call sites (review/external.go and review/independent.go), nowhere else, so the verdict that ends the review also writes its line before the review stops.

Unchanged: `citedScenarios` and the acceptance check, the problem texts, the submit_review schema, verdict handling, the allowance counts, the review_allowance event (its `problems` list still capped at 10 entries), the review event (its `problems` list uncapped) and the candidate/review_invalid stop text. No new configuration. The reviewer prompt golden files under review/testdata (prompts_golden.json) embed the rule and are regenerated with the test-only `-update` flag after this intended change; tests that pin the old rule clause or assert that an exhausted rejection prints no progress line are updated; the single-problem expectations of TestExternalRejectedVerdictRecordsItsProblems and TestIndependentRejectedVerdictRecordsItsProblems keep passing unchanged. kogen-build's testdata/reviewretry/*.wire.json are out of scope.

## Decisions
- The rule clause replacement is the exact text the request gives, applied to the one constant; prompts and tasks keep carrying the constant, not a copy (evidence: review/policy.go; review/parts.go) (source: request)
- One helper `rejectedLine` in review/invalid.go builds the line; K counts the full problem list, never the capped one (evidence: review/invalid.go) (source: request)
- The exhausted-rejection lines are written before invalidStop at the external and native `rejected_verdict_exhausted` sites only (evidence: review/external.go; review/independent.go) (source: request)
- Acceptance drives the behaviour through observations the harness writes itself (a Go test file written into a copy of the checkout by the step file, using the contract suite's fakeExecutor, fakeEnv and the review package's own constants), so no test name the Build must invent is run (evidence: contract/helper_test.go; review/policy_test.go) (source: request)
- The single-problem scenario submits the missing-verdict case `{"findings":[]}` twice, so the review ends exhausted; this keeps the line for one problem exactly as today and gives the scenario a step that fails on the unchanged tree, since an exhausted rejection printed no line before (assumption: the caller accepts one scenario that covers the one-problem line through two refused verdicts) (source: request)
- controls.json is deferred: the correct implementation edits four files and its wrong variants repeat the rule's long source line, which makes whole honest overlay maps impractical within the shaping budget; the Build writes the implementation (assumption: the caller accepts the deferral of the wrong-implementation controls) (source: request)

## Source comparison
- Request item 1 (rule clause): addressed by the policy.go replacement; scenarios "The requirements rule names what an acceptance ref contains" and "Every review prompt carries the new requirements rule once". The reviewer already receives the feature as `# acceptance.feature` in review/material.go; that is unchanged.
- Request item 2 (count in the line): addressed by the helper; scenarios "One rejected problem keeps the progress line unchanged" and "Twelve rejected problems name their total in the progress line". The line of today is built by `r.env.Progress(fmt.Sprintf("kogen: review %d: verdict not accepted: %s", r.in.Number, cutAtWord(problems[0], progressProblemRunes)))` in `allowance`; with one problem it stays the same, with twelve the total is 12, never the capped `(first of 10 problems)`, and one problem never prints `(first of 1 problems)`.
- Request item 3 (line when the review ends): addressed at both call sites that end with `r.invalidStop(problems, "rejected_verdict_exhausted", false)`; scenarios "An exhausted external rejection shows both verdicts in the progress" and "An exhausted native rejection shows both verdicts in the progress", whose two verdicts are each `{"verdict":"approve","findings":[],"requirements":[{"requirement":"R1","evidence":"none","ref":"","met":false},{"requirement":"R2","evidence":"none","ref":"","met":false}]}`.
- Observed evidence of the problem (not scope): a review that was refused and then approved prints `kogen: review 1: verdict not accepted: ` before `kogen: review 1: approve, 0 blocking`; refused refs such as `requirement "Members get 403 on POST account/exports and nothing is sent" cites acceptance "driver test_member_cannot_export_account", which names no scenario of the acceptance result:` and `requirement "Exactly once: no repeat after outcome recorded, fresh claim not re-sent, claim older than 5 minutes sent once" cites acceptance "test_delivery_is_sent_exactly_once", which names no scenario of the acceptance result:` name driver tests; an exhausted review printed only `kogen: review 1: verdict not accepted: requirement "POST account_exports_path: admins and owners only; non-admins get 403 and no export is made; success redirects and enqueues the export job" cites a (1267 s)` for one of six problems.
- Kept as they are: the acceptance check, problem texts, schema, the allowance counts, the event lists and the stop text.
- The request's per-scenario wrong-implementation controls, which would run only the new tests with `go test ./review ./contract -run` and a name pattern, are deferred (see Decisions); this acceptance runs its own focused observations instead of named tests.
