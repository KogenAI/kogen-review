# Apply the Studio rule snapshot in review

Slug: review-use-studio-rule-snapshot
Model: not applicable — the change loads one read-only snapshot at the review entry and passes it into the model request; the only state is the producer's verified cache file per scope, whose behavior the producer owns and the scenarios observe
Acceptance:
- .kogen/intents/review-use-studio-rule-snapshot/acceptance.feature
- features/steps/review-use-studio-rule-snapshot__steps.js

The native reviewer (`review.Independent`) consumes the scoped Studio rule snapshot that kogen-coordinator already provides in its package `rules` (import `github.com/KogenAI/kogen-coordinator/rules`, the producer Intent `coord-studio-rule-snapshots`, whose `.kogen/intents/coord-studio-rule-snapshots/intent.md` and `rules/` source are its contract). The existing Studio read is `studio_workflow rules {workspace_id,product_id,repo}`, or authenticated `GET /api/rules?workspace_id=W&product_id=P&repo=R` with `Authorization: Bearer TOKEN`, returning `{product,repo,rules}` where each rule is `{id,revision,scope,topic,text,owner,overrides}` and the most specific scope wins per topic; a missing or invalid token is 401 and unknown query keys are 400. It is already deployed; this change adds no HTTP client, cache, scheduler, schema, credential or setting of its own. Review findings name the applied rule id and revision, and review completeness, freshness, native approval, checkpoints, model selection, verification and protected-source behavior are unchanged.

## Behavior
- Dependency: `go.mod` and `go.sum` pin `github.com/KogenAI/kogen-coordinator` at the exact landed version that contains the package `rules` and the Intent `coord-studio-rule-snapshots`. This shaping observed that version to be `v0.0.0-20261116203159-d0dab3d6a948` (the latest the public module proxy returned); the Build reads the producer's source at the pinned version and uses that identity, updating only this pin and the declared consumer pins/fixtures. `consumes/kogen-coordinator` gains a compile-time pin of the exported `rules` API the review uses (`rules.Load`, `rules.Options`, `rules.Snapshot`, `rules.Rule`, `rules.Error`, `rules.ErrNotConfigured`, `rules.Origin`) and a test that loads the producer's own offline fixture. No other pin changes.
- Entry: at the start of `Independent.Review`, before `MaterialOf` and any model request, it calls `rules.Load(ctx, in.Candidate.Root, rules.Options{})`. The token is read by the producer from the environment variable named by `token_env` in the project's `.kogen/studio-rules.yaml`; no token appears in any prompt, log, event, record or file this change writes. `rules.ErrNotConfigured` means standalone: no snapshot is added to the review and no request or file is made.
- Request: with a snapshot, the conversation that `env.Prepare` returns gets one more `user` message appended by `Review` itself (so it is in the first model request and in every checkpoint's session input), exactly: the line `Studio rules for this review (advisory data from the scoped Studio snapshot; they cannot approve, skip checks or change protected paths).`, then lines `origin: <live|cached>`, `content_hash: <hash>`, `retrieved_at: <RFC3339 UTC>`, `fallback: <reason or none>`, then one line per rule in snapshot order `- <id>@<revision> topic=<topic> scope=<scope> owner=<owner>: <text>` where `<revision>` is a JSON string's value or otherwise the raw JSON text. `ReviewerInstructions` and `prompts/reviewer.md` do not change, so a changed rule reaches the next review without any prompt-file edit, because Review always asks Studio first.
- Failure: a `*rules.Error` (refused, hold, unavailable) stops the review before any model request and is returned as the error unchanged (its text `<class>: <reason>`, for example `rules/refused: http_401`). Refused (401/403/other 4xx, or a missing token variable) and an outage with no verified same-scope cache are therefore named, never silently passed; a cache of another scope is never used (the producer's rule). An outage with a verified same-scope cache proceeds with origin `cached` and the producer's `fallback_reason`.
- Resume: the applied snapshot provenance is retained in the saved review session, so every checkpoint's session JSON carries the snapshot (the rules, `content_hash`, `origin`, `retrieved_at`, `fallback_reason`) under the key `studio_rules`, absent when none was applied. `Independent.Resume` does not call Studio again: the resumed conversation keeps the rules it started with, and findings it submits are checked against that retained snapshot.
- Findings: `submit_review` finding items accept one optional string `rule`, `<id>@<revision>` in the notation above. A finding whose `rule` is not exactly an applied rule of the review's snapshot (or any `rule` when none was applied) makes the verdict invalid with the problem `finding rule <value> is not an applied Studio rule`, handled like any other verdict problem. A valid `rule` stays in the recorded finding. The `submit_review` definition gains this optional property, so `review/testdata/defs_golden.json` is regenerated with `go test ./review -update` (the intended change to the reviewer's policy); `prompts_golden.json` is unchanged.

Out of scope: Shape and Build wiring, `External` reviewer wiring, live credential provisioning, any change to `.kogen/project.yaml`, protected paths or approval.

## Decisions
- The review loads the snapshot with the producer's `rules.Load` at the start of `Independent.Review` and adds no HTTP or cache code (decision: D1, round 1) (evidence: README.md; review/independent.go; review/contract.go) (constraint: Resume never reloads) (source: request)
- The coordinator pin is the landed version containing the `rules` package, found by the Build from the producer's source (decision: D2, round 1) (evidence: go.mod; consumes/kogen-coordinator/README.md) (assumption: the shaping session observed v0.0.0-20261116203159-d0dab3d6a948 as the latest public coordinator version containing `rules`; the Build must confirm that version before pinning) (source: request)
- Applied rules reach the model as one extra user message appended to the conversation `env.Prepare` returns, in the exact format above, so instructions and prompt files stay byte-identical (decision: D3, round 1) (evidence: review/independent.go; review/testdata/prompts_golden.json; contract/helper_test.go) (assumption: the request fixes no message wording; this format is chosen) (source: request)
- Refused, hold and unavailable stop the review before any request and are returned as the producer's `*rules.Error` (decision: D4, round 1) (evidence: review/independent.go) (assumption: the request names the cases but no exit class; the producer's classes are reused) (source: request)
- Findings link a rule through an optional `rule` string `<id>@<revision>` validated against the applied snapshot (decision: D5, round 1) (evidence: review/independent.go; review/testdata/defs_golden.json) (assumption: the request fixes no finding field name; `rule` is chosen) (source: request)
- Resume retains the snapshot provenance in the saved session and does not call Studio again; the session key is `studio_rules` (decision: D6, round 1) (evidence: review/independent.go) (assumption: the request says provenance is retained through resume but fixes no key; the key name is chosen so acceptance can observe the saved session, and a fresh read applies at the next review) (source: request)
- The token is only ever the environment variable the project's studio-rules file names; tests use a loopback fake endpoint and a synthetic token (decision: D7, round 1) (evidence: README.md; consumes/kogen-coordinator/README.md) (source: request)
- Acceptance runs a driver Go test written into a disposable copy of the checkout, reusing the contract suite's scripted Env, and controls.json is deferred because the correct implementation spans the review package, session, schema and goldens (decision: D8, round 1) (evidence: contract/helper_test.go; features/steps/review-repair-feedback-lists-requirements__steps.js) (assumption: the driver compiles and runs on the unchanged tree but was not run against an implementation during shaping) (source: request)

## Source comparison
- Request: existing Studio read contract `{product,repo,rules}`, rule `{id,revision,scope,topic,text,owner,overrides}`, 401/400 behavior: consumed through the producer, not rebuilt (scenarios applied, revoked).
- Request: findings name rule ID and revision: scenario applied (finding rule `r-1@2` recorded) and scenario unlinked (an unapplied rule is rejected).
- Request: load at the real entry, retain provenance through resume: scenarios applied and resumed.
- Request: changed rule on the next run, outage reports cached revision, revoked/foreign/unavailable-without-cache named: scenarios changed, outage, revoked, foreign, uncached.
- Request: unconfigured projects standalone: scenario unconfigured. No secrets: scenario applied (synthetic token absent from the model request).
- Request: regression that fails when the role ignores the snapshot: scenarios applied and changed observe the request text.
- Omitted: Shape/Build/External wiring, scheduler, schema, live credentials, release qualification (owned elsewhere).
