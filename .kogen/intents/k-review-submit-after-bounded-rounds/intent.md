Bound the native reviewer's working requests before prompting for a verdict. Currently a reviewer can indefinitely answer with read_file or shell and never spend either existing allowance, while each model request resends its conversation. Allow twelve model requests (four times the instructions' approximately three working rounds). If no valid verdict has ended the conversation, request thirteen and every subsequent request must carry the budget notice and require submit_review wherever the existing route capability supports it. This is a submission prompt, not a maximum request count, automatic approval, or a new invalid-stop allowance. Do not change the external executor workflow, transport, model instructions, tool definitions, verdict validation or review repair limits.

## Decisions
- Ordinary reviews and a review submitting on its third request keep their existing model-facing request sequence and bytes; no budget message or extra request before the threshold. A valid submission ends the conversation without another request. (source: request)
- Keep the two existing independent one-use rejected-verdict and prose-only allowances, including unread-progress exemptions, exactly as they are. Budget exhaustion itself spends neither allowance. (source: request)
- Unread parts still prevent approval; changes still needs a blocking finding and read parts. A forced submission is validated through the same path as any submission. Unread progress can require further reading and submission; the budget prompt must not make that impossible. (source: request)
- Count model requests cumulatively in the review's own saved Session; interruption and working-window reset do not replenish the count. (source: request)

Technical settlement: use twelve as the fixed bound, not a new setting. Add an optional integer Session JSON field `requests`, default zero for older saved sessions. Increment once for each invocation of Env.Request, including a request that returns an interruption; internal provider attempts are not separate review requests. Save the incremented count before sending and include it in Request.Retain's session with the actual working-window input. Preserve it across Session reconstructions, verification/repair feedback and resume rather than deriving it from Input length. No change is needed in a consumer to carry an optional Session JSON field. Update local session format coverage as needed while retaining backward decoding and the existing API.

Use this exact user-message text when the pre-request cumulative count is at least twelve: `Your review working budget is spent. Call submit_review now with what you know; verdict validation and unread-part requirements still apply.` Ensure it is present in the request's conversation after any working-window preparation; retain it with that conversation. Avoid appending duplicate identical notices when one is already present in the active input. Where SupportsToolChoice already returns true, set Request.ForceTool to SubmitReviewTool for each over-budget request. Where false, leave ForceTool empty and send the same notice as text. Combine, rather than independently duplicate, any existing pending prose-only reminder forcing. After the budget, a text-only answer spends the existing prose-only allowance (or exhausts it); an invalid verdict follows existing rejection and unread-progress rules. Never relax validation to meet the budget. Do not add a new stop for a provider that ignores forced choice but keeps calling working tools.

The acceptance adapter reuses contract.newReview's real temporary Git candidate and real native read_file tool, while overriding only Env.Request to script model responses and record outgoing requests/retained state. It runs the submitted TestBudgetAcceptanceDriver in a disposable copy, not a test the builder must invent. It emits JSON observations to BUDGET_RESULT and uses BUDGET_CASE for one bounded script. The script's maximum is fifteen requests (or fourteen for prose fallback), so an unfixed reviewer cannot hang. For the long case it reads for twelve requests and submits on thirteen; the observer independently demands forcing and notice on thirteen, cumulative retained counts, and exactly thirteen requests. The unread case attempts approval on thirteen, reads on fourteen, and approves on fifteen; no premature approval is accepted. The interruption case interrupts request seven, retains replacement working-window input, then resumes the same checkpoint; counts and forcing must remain cumulative. These are synthetic local provider-boundary tests, not claims about a live provider.
