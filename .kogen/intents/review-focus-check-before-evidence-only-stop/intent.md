# Ask for a focused check before an evidence-only

Slug: review-focus-check-before-evidence-only-stop
Model: not applicable — each rule judges one submission against the review's recorded shell runs and the requirements it listed; the review loop's stages, allowances, checkpoints and stop classes keep their transitions
Acceptance:

Studio Build 9c5e6662 stopped on a paired-key requirement after the native reviewer made 14 calls, four context resets and only pwd, git status and git diff shell calls. It ran no focused check, and its changes verdict was accepted because the blocking finding quoted the requirement. A later model-free probe found both omission cases refused without effects, so the stop rested on a missing check, not on a demonstrated defect. After this change the native review, when it is about to stop solely because an explicit requirement has no evidence, first returns the exact missing condition and asks for one focused candidate-bound check, or for the concrete reason it cannot safely run. This is delivered once per unresolved requirement on the same candidate. If evidence stays unavailable the candidate is kept and the requirement is reported as unverified. The approval gate, scope, sandbox, cancellation and evidence checks stay as they are.

The interface, all in package `review` (module `github.com/KogenAI/kogen-review`):

1. Session (`review/independent.go`) gains `FocusRequested []FocusRequest` with JSON tag `focus_requested,omitempty`. A new exported type `FocusRequest` has `Tree string` (`tree`: the candidate's tree, `candidateTree`, when the request was made) and `Requirement string` (`requirement`: the requirement's stored text). Sessions without it encode exactly as today. The `Session` literals that `retry` and `evaluate` rebuild carry it forward as they carry `Listed`; checkpoints, resumes and working-window resets keep it.

2. Trigger (`run.validate`, native reviewer only, after every existing check found no problem). A `changes` verdict is an *evidence-only stop* when all of these hold: its `requirements` array has at least one entry with `met` false; every entry with `met` false has evidence `none`; every blocking finding quotes (as `quotes` does) at least one of those entries; no `ProbeRun` of this review names a file or directory of the current tree (as the existing probe check decides it); and no `ProbeRun` of this review has `Refused`. For such a verdict, each unmet entry whose identity has no `FocusRequested` entry with the current tree is a *pending request*. If there is one or more, the submission is refused: its problems are one text per pending request, in the verdict's order, each recorded in `FocusRequested` with the current tree, and the verdict is not accepted. The text, with `<R>` the requirement's stored text verbatim:
   `requirement "<R>" has no evidence, and that is the only ground of this changes verdict: no focused check of the candidate has run in this review and no tool or environment limitation is recorded. A missing check is unverified, not a defect of the candidate. Run one focused check of this requirement with shell on the current tree and cite its exact command, or, when it cannot safely run here, submit the same changes verdict with a blocking finding that states the concrete reason it cannot run`
   It reaches the reviewer as the usual tool result `invalid verdict:` followed by a newline and the problems, one per line. This refusal does not spend the rejected-verdict allowance. A changes verdict that is not an evidence-only stop, or whose entries all have a request on this tree, is accepted as today.

3. Approval is unchanged. An `approve` clears a requirement only by the existing rules: a cited probe must have run in this review, succeeded and been run on the current tree, a cited acceptance scenario must have passed on it, and a requirement listed by an accepted submission cannot be dropped. Evidence recorded for an older tree and a probe that never ran are refused with their existing problems and with no focus request.

4. Stop report (`run.evaluate`, native reviewer only). When a `changes` verdict is accepted and has entries with `met` false and evidence `none`, each is reported unverified with a state: `refused` when a `ProbeRun` of this review has `Refused`; otherwise `attempted` when a `ProbeRun` names a file or directory of the tree the verdict judged; otherwise `unavailable`. The `candidate/review_blocked` stop gets, after its `review: <path>:<line>: <message>` lines, one line `review: unverified requirement "<R>": focused check <state>` per such entry in the verdict's order, and `review-<n>.json` gets `unverified`, a list of `{"requirement": <R>, "check": <state>}`, absent when none. The candidate's files are left as they are.

The reviewer's model-facing policy does not change: `ReviewerInstructions()`, `review/prompts/reviewer.md`, the `submit_review` definition, the external review task and both goldens stay byte-for-byte as they are; the new text reaches a reviewer only as a refused submission's problem. The external reviewer is unchanged.

## Decisions
- A native changes verdict is an evidence-only stop, and gets the targeted request, only when its requirements array has at least one unmet entry, every unmet entry has evidence none, every blocking finding quotes one of those entries, and this review recorded no focused check (a ProbeRun naming a file or directory of the current tree) and no limitation (a ProbeRun with Refused) (decision: D1, round 1) (constraint: External reviewers are unchanged) (constraint: The reviewer prompt, the submit_review definition and both goldens stay byte-for-byte as they are) (evidence: review/independent.go; review/contract.go; review/prompts/reviewer.md) (assumption: What counts as a focused check reuses the existing rule that a probe names a file or directory of the current tree; a reviewer whose check names no candidate path is still asked once.) (source: request)
- The request is delivered once per unresolved requirement on the same candidate: Session records (tree, requirement) pairs in focus_requested, written when the request is made, carried through retry and evaluate rebuilds, and kept by checkpoints, resume and reset. A repeated or duplicate unsupported evidence-only submission on the same tree is then accepted as a blocking verdict and is not prompted again. Another tree prompts again. (decision: D2, round 1) (constraint: Sessions without the field encode exactly as today) (evidence: review/independent.go; review/reset.go) (assumption: Keyed by the requirement identity (trimmed, whitespace-folded, case-insensitive) as the existing requirement ledger does.) (source: request)
- The targeted request travels as the problems of a refused submit_review, a tool result starting invalid verdict:, and does not spend the one rejected-verdict allowance (evidence: review/independent.go; review/invalid.go) (assumption: Not consuming the allowance is a product choice the request does not state; the alternative would end the review invalid on a second refusal.) (source: request)
- When the review stops on a changes verdict with unmet evidence-none requirements, each is reported unverified with how its check went: refused (a ProbeRun of this review has Refused), attempted (a ProbeRun names a candidate path), otherwise unavailable. The report is a line in the stop's lines, review: unverified requirement "<text>": focused check <state>, and an unverified list of {requirement, check} in the review record; the candidate is kept as today. (constraint: Native reviewer only; nothing is reported when no evidence-none requirement is unmet) (evidence: review/independent.go; review/contract.go) (assumption: The wording of the report line and the key name unverified are chosen by this shaping; the request names only the three states.) (source: request)
- An approval clears a requirement only through the existing evidence rules: a cited probe must have run in this review, succeeded and been run on the current tree. Evidence of an older tree and a probe that was never run are refused exactly as today, with no new feedback request. The independent approval gate, scope, sandbox, cancellation and evidence checks are unchanged. (decision: D5, round 1) (evidence: review/independent.go; .kogen/intents/k-review-unrun-evidence-not-met/intent.md) (source: request)

(source: request)
- The targeted request travels as the problems of a refused submit_review, a tool result starting invalid verdict:, and does not spend the one rejected-verdict allowance (decision: D3, round 1) (evidence: review/independent.go; review/invalid.go) (source: request)

## Source comparison
- "When the reviewer is about to stop solely because an explicit requirement has no evidence, and there is no recorded focused check or concrete tool/environment limitation, return the exact missing condition and ask for one focused candidate-bound check ... or for the concrete reason it cannot safely run": item 2, its trigger and its text. Scenario "An evidence-free objection after inspection gets one request for the missing check" replays the 9c5e6662 pattern with pwd, git status and git diff and a paired-key requirement (the fixture's requirement `A grant needs both a name and a key: omitting either is refused and writes nothing`, whose two omitted-input cases the focused check runs).
- "Deliver that feedback once per unresolved requirement on the same candidate through context reset or saved-review continuation": item 1, covered through saved-review continuation by scenario "The request is not repeated after the review resumes from its checkpoint" and for context reset by the integration test below, because a reset keeps the session it rewrites.
- "If evidence remains unavailable, retain the candidate and report the unresolved requirement as unverified, including whether the check was attempted/refused or unavailable": item 4; scenarios "A check that could not run is reported unverified and a repeated submission is not prompted again" (unavailable, and the duplicate submission) and "A check the restriction refused is reported unverified without a request" (refused). The attempted state is covered by the integration test.
- "A directly evidenced defect still blocks immediately; the same-tree green evidence path accepts without extra calls": scenarios "A defect shown by a failing check blocks at once" and "Same-tree green evidence approves without extra calls".
- "Stale-tree evidence and a probe that was never run still cannot approve", each standing on existing behaviour alone: scenarios "Evidence of an older tree cannot approve" and "A probe that never ran cannot approve", which end invalid with the existing problems and make no focus request. Wrong implementations that accept either are caught because the Then step expecting the refusal fails.
- "Keep the independent approval gate and existing scope, sandbox, cancellation and evidence checks", "Scope this to Review's existing evidence feedback and stop reporting": item 3 and the unchanged prompt and goldens. Omitted by the request: Studio's r3 omitted-key messages, Factory dispatch and custody, any new default, setting or paid rerun of the original.
- Controls: controls.json is deferred (decision D6); the observer controls are declared in Feasibility.

## Tests
- An evidence-free changes verdict after only inspection tools is sent back once with the targeted text, then a focused check cited on the same tree approves with no other call: scenario "An evidence-free objection after inspection gets one request for the missing check" (scenario)
- A changes verdict whose requirement evidence is a probe that ran blocks at once with no unverified report: scenario "A defect shown by a failing check blocks at once" (scenario)
- An approval citing a probe that ran and succeeded on the current tree is accepted with no extra request: scenario "Same-tree green evidence approves without extra calls" (scenario)
- A repeated evidence-only changes verdict on the same tree is accepted and reported unverified with check unavailable, the candidate unchanged: scenario "A check that could not run is reported unverified and a repeated submission is not prompted again" (scenario)
- A refused focused check recorded by the restriction gets no request and is reported unverified with check refused: scenario "A check the restriction refused is reported unverified without a request" (scenario)
- The request is not made again after the review resumes from its saved checkpoint: scenario "The request is not repeated after the review resumes from its checkpoint" (scenario)
- An approval citing a probe whose latest run was on an older tree is refused with the existing problem and no focus request: scenario "Evidence of an older tree cannot approve" (scenario)
- An approval citing a probe that never ran is refused with the existing problem and no focus request: scenario "A probe that never ran cannot approve" (scenario)
- The trigger boundaries and states through the review conversation over a fake Env: no request when the requirement list is absent, when an unmet entry has evidence probe or acceptance, when a finding quotes no unmet evidence-none entry, or when a ProbeRun names a candidate path; one request per requirement and tree; a new request after the tree changed; the unverified state attempted for a recorded focused check; the request not spending the rejected-verdict allowance; focus_requested kept through retry, evaluate, a saved checkpoint and a working-window reset (a sessions without it decoding and encoding as before): add to `contract/independent_test.go` and `contract/reset_test.go` (integration)
