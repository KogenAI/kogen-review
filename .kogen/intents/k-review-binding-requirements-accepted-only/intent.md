# Bind only accepted review requirements

Slug: k-review-binding-requirements-accepted-only
Model: not applicable — one rule changes when a submission's requirement texts join the review's list (`Session.Listed`), checked per submit_review call; the review loop's stages, allowances, checkpoints and stop classes keep their transitions
Acceptance:
- .kogen/intents/k-review-binding-requirements-accepted-only/acceptance.feature
- features/steps/k-review-binding-requirements-accepted-only__steps.js
- features/steps/k-review-binding-requirements-accepted-only__driver.js

An independent review lists the requirements it checked, with the evidence for each, every time it submits a verdict (`submit_review`'s `requirements`). Today `run.requirements` in `review/independent.go` appends the texts of every well-formed `requirements` array to `Session.Listed` while it validates the submission, whether the submission is then accepted or refused. A later approval of the same review that drops one of those texts is refused with `requirement "<R>" was listed by an earlier submission of this review and is missing: keep every requirement in requirements, with evidence observed on the current tree`. A review also gets exactly one refused submission before it ends without a verdict (`candidate/review_invalid`). Together the two rules trap a reviewer that does what it was told. Its first submission is refused for an evidence problem, which spends the one refusal. It repairs the submission, for example by splitting one requirement into several or rewording them. The repair is then refused only because the refused submission's original wording is "missing", and the review ends invalid although every requirement of the repair has valid evidence.

After this change, only the requirement texts of an accepted submission are added to `Session.Listed` and bind later approvals of the same review. A refused submission lists nothing: its texts are not recorded, and a later approval may reword, split, merge or omit them. A submission is refused when its validation (`run.validate`) returns any problem, of any kind: findings, requirements, evidence or unread parts. It is accepted when `run.validate` returns a verdict. An accepted approval that the review then sends back for another round (for example because Kogen's verification of the reviewer's own edit is red) was still accepted, so its texts stay binding.

The rule, in `run.validate` and `run.requirements` (`review/independent.go`). They are reached by the native reviewer's `submit_review` calls, the external reviewer's structured verdicts (`External.verdictOf`) and `review.Validate`, so all three follow it:

1. `run.requirements` no longer changes `Session.Listed`. It still groups a well-formed array's entries by identity (`identity`: trimmed, each run of whitespace as one space, letter case ignored). A group's stored text is the text of `Session.Listed` with the same identity when there is one, and otherwise the group's first entry's text.
2. When `run.validate` accepts the submission, it appends to `Session.Listed` the stored text of each accepted requirement (`Verdict.Requirements`) whose identity no text of `Session.Listed` has, in the order of `Verdict.Requirements`. So `Session.Listed` keeps each identity once, in its first accepted spelling, in the order first accepted. A refused submission leaves `Session.Listed` unchanged, and so does an accepted submission with `requirements` absent, `null` or `[]`.
3. Everything else stays as it is. An approval is still checked against `Session.Listed` as it stood before the submission, so it gets the missing problem for each listed text whose identity it lacks, in `Listed` order and quoting the listed text. The other problem texts are unchanged: the shape problem, `is listed twice`, the evidence problems (no evidence, not met, probe not run, probe naming nothing of the tree, failed or older-tree probe, and the acceptance not_run, other tree, no scenario, failed and not-passed problems) and the changes-verdict quote check. Requirement identity and the one allowed refusal are unchanged, as are the `Session` JSON key `listed_requirements`, the reconstruction of `Session` in `retry` and `evaluate` (which carries `Listed` forward), `review-<n>.json`, the stop classes, the reviewer's instructions and `submit_review` definition (and so both goldens), and `cmd/kogen-review`.
4. A checkpoint saved before this change keeps the `listed_requirements` it was saved with. Nothing is migrated.

Examples: the review's first submission lists `R1` citing acceptance `Print the receipt of a total`, which names no scenario of the pass, and is refused. Its second submission lists `R1a` and `R1b` with valid evidence. It is accepted, the review approves, `review-1.json` keeps `R1a` and `R1b`, and the saved checkpoint's `listed_requirements` is `["R1a","R1b"]`. In another review, an accepted approval lists `R1`, `R2`, `R3` and is sent back after a red verification of the reviewer's edit. A next approval that lists only `R1` and `R2` is refused with exactly one problem, the missing problem naming `R3`.

The implementation also updates the doc comments of `Session.Listed` (today "accepted or refused") and `run.requirements`, and the `session-listed` item of `contract/README.md`, to say that only accepted submissions list requirements.

## Decisions
- Only the requirement texts of an accepted submission become binding for later approvals of the same review; a refused submission lists nothing, and a later approval may reword, split, merge or omit its texts (source: request)
- A later approval that drops a requirement an accepted earlier submission listed is still refused, naming it, and is accepted once it restores it (source: request)
- Requirement identity (trimmed, whitespace collapsed, case ignored), the first accepted spelling as the stored one, the "listed twice" refusal, the evidence checks and the one allowed refusal are unchanged (source: request)
- A saved review checkpoint lists only what its accepted submissions listed (source: request)
- A submission is accepted exactly when run.validate returns a verdict, and only then are its requirement texts appended to Session.Listed. run.requirements no longer mutates Session.Listed. Native, external (verdictOf) and review.Validate all share this rule.
